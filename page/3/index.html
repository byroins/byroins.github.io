1.0 介绍

在上一篇文章[Union Injection]中, 逐步剖析了数字型注入(Less-2)关卡, 这篇文章开始转向字符型注入,他增加了一个关键步骤: 符号闭合,也就是通过精心拼接单引号、双引号或括号，把原本破坏 SQL 语法的恶意输入“伪装”成合法的查询语句，从而成功注入我们想要的 Payload

在真实 Web 应用中，绝大多数用户输入的参数都是被引号包裹的字符串(如登录名、搜索关键词、文章标题),字符型注入的占比远高于数字型

网络通讯协议—IP

Posted on 2026-04-05 Edited on 2026-10-13 In network , ip

IP协议

1.0 IP地址

1.0.1 IP地址进制表示

  • IP地址由32bits二进制数字序列组成，分为4段，每段8位；

    最小值：00000000；最大值：11111111；对应的十进制为0和255；

  • 为方便记忆，将序列转换为10进制，即点分十进制。

  • 例如计算本机IP二进制表示信息：192.168.31.85

    思路：

    192>128 => 10000000; 192-128=64 => 01000000 第一段 => 11000000

    168>128 => 10000000; 168-128=40 < 64; 40>32…第二段 => 10101000

    第三段 => 00011111; 第四段 => 01010101

    所以 192.168.31.85 == 11000000.10101000.00011111.01010101(二进制)

  • 逆向计算(二进制转十进制)

    10011111 => x(10)?

    思路：利用逻辑运算方式，上一个例子中计算同样是按照此方式，只是将2^n转换成具体的数值计算

    2^7 + 2^4 + 2^3 + 2^2 + 2^1 + 2^0 = 128+16+8+4+2+1 = 159

1.0.2 IP地址逻辑运算

  • 逻辑与(AND)运算：求网络号

    规则：全为1才1，有0则0

    作用：用掩码将IP地址中主机位全部清零，只保留网络位，算出IP属于哪个子网

  • 逻辑或(OR)运算：求广播地址

    规则：有1则1

    作用：把主机位强制全置为 1，得到该网段的广播地址。

3.0 网络地址子网划分

3.0.1 网络掩码概念

  • 网络掩码与IP地址搭配使用，用于描述一个IP地址中的网络部分及主机部分，根据划分后的主机部分，随之可得出可拥有的主机范围；

  • 网络掩码32bits，与32bits的IP地址相对应，掩码中为1的位对应IP地址中的网络位，掩码中为0的位对应IP地址中的主机位。(网络位1,主机位0)

网络通讯协议—DHCP-DNS

Posted on 2026-04-04 Edited on 2026-10-15 In network , DHCP-DNS

1.0 DHCP

一台主机接入网络后要能正常通信，至少需要四样参数：IP 地址、子网掩码、默认网关、DNS 服务器地址。几台机器手工配置没有问题，几十上百台机器的网络里无法维护，换一个网段就要全部重配一遍。DHCP（Dynamic Host Configuration Protocol，动态主机配置协议）把这四样参数连同租期一起自动下发。

DHCP 工作在应用层，基于 UDP：服务端使用 67 端口，客户端使用 68 端口。协议由 BOOTP 扩展而来，因此在抓包工具里过滤 DHCP 报文要使用 bootp 过滤器而不是 dhcp。

1.1 报文格式

DHCP 报文分成两段：固定长度的头部，以及可变长的选项字段。

字段 长度 说明
OP 1字节 报文类型，1 = 请求，2 = 应答
HTYPE 1字节 硬件类型，以太网为 1
HLEN 1字节 硬件地址长度，以太网 MAC 为 6
HOPS 1字节 经过的 DHCP 中继跳数，客户端置 0，每经过一个中继加 1，用来防止环回
XID 4字节 事务 ID，客户端随机生成，用来把请求与应答配对
SECS 2字节 客户端从开始申请到此刻经过的秒数
FLAGS 2字节 最高位置 1 表示要求服务端以广播方式应答
CIADDR 4字节 客户端已有的 IP 地址，首次申请时为 0.0.0.0
YIADDR 4字节 服务端分配给客户端的 IP 地址
SIADDR 4字节 下一个为客户端提供服务的服务器地址
GIADDR 4字节 中继代理的地址，跨网段时由中继填入
CHADDR 16字节 客户端硬件地址，即网卡 MAC
SNAME 64字节 服务器名称，可选
FILE 128字节 启动文件名，无盘工作站网卡启动时使用
Options 可变 以魔术字 0x63825363 开始，所有实际参数都在这里

头部只规定了地址填在哪一格，真正决定下发什么参数的是 Options。

选项码 名称 说明
53 DHCP Message Type 报文类型，决定这条报文是 DISCOVER / OFFER / REQUEST / ACK 中的哪一种
50 Requested IP Address 客户端希望申请的地址
54 Server Identifier 客户端选中的服务器地址
51 IP Address Lease Time 租期
58 Renewal (T1) Time 续约时间点
59 Rebinding (T2) Time 重绑时间点
1 Subnet Mask 子网掩码
3 Router 默认网关，可以下发多个
6 Domain Name Server DNS 服务器地址
15 Domain Name 域名，用于把无后缀的主机名补全

1.2 交互过程

首次获取地址要交换四条报文，取首字母简称 DORA。

除了这四条，还有三种报文。

报文 Options 53 方向 触发场景
DHCP NAK 6 服务端 → 客户端 拒绝 REQUEST，例如申请的地址不在地址池内，或已经租给别的客户端。客户端收到后重新从 DISCOVER 开始
DHCP DECLINE 4 客户端 → 服务端 免费 ARP 检测到地址冲突，告知服务器这个地址不能用
DHCP RELEASE 7 客户端 → 服务端 客户端主动放弃地址，提前归还给地址池

DISCOVER 和 REQUEST 都用广播，原因是一致的：在拿到 ACK 之前，客户端并不知道自己会被分配哪个地址，也就无法用目的 IP 寻址，只能依赖二层广播送出，由网段内的主机接收后，再交给运行 DHCP 服务的进程判断是否处理。

引申：DHCP 协议本身没有任何认证机制，网段内任何一台主机都可以起一个 DHCP 服务并应答 DISCOVER。伪造的服务器只要抢先应答，就能把自己的地址作为网关和 DNS 下发，客户端之后的所有流量都先经过攻击者。为了确保抢到应答，攻击者通常先做 DHCP 饿死攻击（DHCP Starvation），用伪造源 MAC 的大量 DISCOVER 报文把真实服务器的地址池耗尽，此时伪造服务器就成了唯一应答方。企业网络里对应的防护是交换机端口的 DHCP Snooping，只信任连接合法服务器的那个端口。

1.3 租期与续约

DHCP 分配的是租期，不是永久占用。主机下线后如果地址一直被占着，地址池很快会不够用。

1.4 DHCP 中继

路由器不转发广播报文，而 DISCOVER 就是广播，因此 DHCP 服务器与客户端必须处在同一个广播域内。一栋楼有几十个网段，如果每一段都部署一台 DHCP 服务器，维护成本无法接受。

DHCP 中继（Relay Agent）用来解决这个问题：网关设备在本地网段接收客户端的广播，转成单播发给远端 DHCP 服务器，同时把收到广播的那个接口地址写进 GIADDR 字段。服务器依据 GIADDR 判断客户端属于哪个网段，从对应的地址池里取地址。

1.5 抓包观察

观察重点是 Options 53 的取值如何依次变化，以及 YIADDR 在哪一条报文里被填上。DISCOVER 的 XID 与后续三条完全一致，这是把它们串成一次完整交互的依据。

2.0 DNS

DHCP 下发的参数里有 DNS 服务器地址，因为人记不住 IP。DNS（Domain Name System，域名系统）负责把域名与地址对应起来。

2.1 域名结构

域名是一棵树，从右往左逐级细化，各级之间用点分隔，最右边是通常省略的根。

  • 根域用单个点表示，写作 .
  • 顶级域分两类：通用顶级域 gTLD（com、net、org、edu）和国家地区顶级域 ccTLD（cn、jp、uk）
  • 每一级标签不超过 63 字节，完整域名不超过 253 字节
  • 域名不区分大小写
  • 写成 www.example.com. 时末尾那个点表示根，这种写法叫 FQDN（完全限定域名），配置文件里要求写全

2.2 查询过程

DNS 查询分两种，区别在于谁去跑腿。

  • 递归查询：客户端向本地 DNS 服务器发出一次请求，服务器必须返回最终结果，不允许只回一句”下一步该问谁”
  • 迭代查询：本地 DNS 服务器向根、顶级域、权威服务器逐级询问，每一级返回的是”下一步该问谁”

从在浏览器里敲下一个域名到真正发出请求，中间还会经过几层缓存和本地配置，全都未命中才会走到上面的迭代查询：

  • hosts 文件里的静态映射不经过网络，本地 DNS 服务器也无法覆盖它。Linux 在 /etc/hosts，Windows 在 C:\Windows\System32\drivers\etc\hosts
  • Linux 上本地 DNS 服务器的地址写在 /etc/resolv.conf，Windows 上执行 ipconfig /all 查看
  • 查询与应答默认走 UDP 53。应答长度超过 512 字节时会被截断（Flags 中 TC 位置 1），客户端改用 TCP 53 重新发送；区域传送（AXFR）和 DNSSEC 也必须使用 TCP

2.3 报文格式

DNS 只有一种报文格式，靠 Flags 里的 QR 位区分查询和应答。

头部长度固定 12 字节。

字段 长度 说明
ID 2字节 事务 ID，用来把查询与应答配对
Flags 2字节 标志位，见下表
QDCOUNT 2字节 问题段记录数
ANCOUNT 2字节 回答段记录数
NSCOUNT 2字节 权威段记录数
ARCOUNT 2字节 附加段记录数

Flags 字段的各位：

位 名称 说明
QR 查询/应答 0 = 查询，1 = 应答
Opcode 操作码 0 = 标准查询，5 = 动态更新
AA 权威回答 该应答来自本域的权威服务器
TC 截断 应答超过 512 字节被截断，需要用 TCP 重发
RD 期望递归 客户端置 1，要求服务器完成递归查询
RA 递归可用 服务器置 1，表示自己支持递归
RCODE 返回码 0 = 成功，3 = 域名不存在（NXDOMAIN），5 = 拒绝

头部之后是四段，顺序固定：问题段（Question）、回答段（Answer）、权威段（Authority）、附加段（Additional）。问题段里是要查的名字加查询类型，回答段里是一条条资源记录，权威段在没有答案时用来指出谁才是权威，附加段携带 NS 与 MX 记录所指向主机的地址，省掉一次额外查询。

2.4 资源记录类型

类型 用途 示例
A 域名到 IPv4 地址，最常用 www.example.com. 300 IN A 203.0.113.10
AAAA 域名到 IPv6 地址 www.example.com. 300 IN AAAA 2001:db8::10
CNAME 别名，把域名指向另一个域名 blog.example.com. 300 IN CNAME www.example.com.
MX 邮件交换记录，带优先级数字，数字越小越优先 example.com. 3600 IN MX 10 mail.example.com.
NS 该域的权威 DNS 服务器 example.com. 3600 IN NS ns1.example.com.
PTR 反向解析，由 IP 查域名，记录写在 in-addr.arpa 域下 10.113.0.203.in-addr.arpa. 300 IN PTR www.example.com.
SOA 区域起始授权记录，描述区域的权威、序列号和各时间参数，每个区域有且只有一条 通常与 NS 记录一同返回
TXT 文本记录，常用于 SPF、DKIM 和域名所有权验证 example.com. 300 IN TXT "v=spf1 include:..."
SRV 服务定位，标明服务所在主机与端口 _sip._tcp.example.com. 300 IN SRV 10 5 5060 sip.example.com.
CAA 指定允许为该域签发证书的 CA example.com. 300 IN CAA 0 issue "letsencrypt.org"

引申：DNS 记录本身就是一份资产清单。NS 记录指出权威服务器，MX 记录指出邮件服务，TXT 记录里往往写着第三方服务的域名，CNAME 会暴露业务用了哪家的对象存储或 CDN。子域名爆破、证书透明日志查询，目的都是把这份清单补全。区域传送如果被错误放行，一次 AXFR 请求就能拿到整份记录。

2.5 缓存与 TTL

资源记录里的那个数字就是 TTL。

  • TTL 由该域名的权威服务器设定，本地 DNS 服务器和操作系统都按它缓存，缓存期内不再发起查询
  • TTL 取小了（例如 60 秒），记录变更后生效快，代价是查询量上升；取大了（例如 86400 秒），查询量小，改完要等很久才全网生效
  • 查不到的域名也会被缓存。NXDOMAIN 的负缓存时长由 SOA 记录里的 minimum 字段决定
  • 改动本机 hosts 文件立即生效，但浏览器可能还有自己的一层缓存

2.6 查询工具

dig +trace 的输出就是 2.2 节迭代查询流程的实际展开，逐级看到的 NS 记录就是那句”下一步该问谁”；dig 返回头部里的 flags: qr rd ra 正好对应 2.3 节 Flags 字段的各位。

引申：DNS 在渗透里还有一个方向是流量控制。DNS 查询几乎不会被出口防火墙拦下，把数据编码进查询名再发出去，就是一种能绕过访问管控的出网通道，也就是 DNS 隧道。反过来的方向是篡改，客户端拿到伪造的解析结果后就会连到攻击者的服务器上，这也是内网里伪造 DNS 服务器比伪造网关更隐蔽的原因。

网络通讯协议—HTTP

Posted on 2026-04-03 Edited on 2026-10-15 In network , http

1.0 HTTP协议

超文本传输协议, 使用一种用于消息的模型: (客户端发出一条请求消息, 由服务器返回一条响应消息)

1.1 请求(Request)报文

所有HTTP消息(请求与响应)中都包含:

  • 1个或n个单行显示的消息头(header) 主要包含: 请求行信息和请求头信息;
  • 1个强制空白行;
  • 请求消息主体(可能存在);

01 报文详解: 请求行

序号 参考内容 解释说明
1 GET 表示向服务端请求数据资源的方法
2 /dz..227 表示向服务端具体需要请求的资源信息
3 HTTP/1.1 表示和服务端进行HTTP通讯过程选择的协议版本

02 请求方法

GET: 从服务器获取资源。参数全部拼接在URL中，格式为?key1=value1&key2=value2

POST: 向服务器提交数据，数据在请求体（Body）中，不在URL里。常见于登录、注册、文件上传、评论区

HEAD: 与GET完全相同，但服务器只返回响应头，不返回响应体。用来快速判断一个URL是否存在、资源有多大，而不消耗大量带宽

OPTIONS: 查询服务器对某个URL支持哪些HTTP请求方法

PUT: 向指定URL上传或更新资源。与POST不同，PUT是幂等的（多次相同请求结果一致），通常对应文件级别的操作

引申：这几个方法在测试里对应不同的入口。GET 与 POST 的差别只是参数放的位置，注入类漏洞的判断方式一致；OPTIONS 可以探测目标允许哪些方法；TRACE 会把请求原样回显给客户端，历史上被用来读取带 HttpOnly 标记的 Cookie；PUT 若被开启，往往意味着可以直接上传文件覆盖服务器上的现有资源。

03 报文详解: 请求头

请求头字段解读: Accept
  • Accept 表示浏览器支持的MIME类型[斜杠/前面的是类型(type); 斜杠/ 后面的是子类型(subtype)]
  • type指定大范围,subtype是type中更明确的类型;

常见的MIME类型:

序号 类型 解释说明
01 Text 标准化展示文本信息,文本消息可以是多种字符集或者多种格式;
Text/HTML 表示HTML文档;
02 Application 用于传输应用程序数据或者二进制数据;
application/xhtml+xml xhtml文档;
application/xml xml文档
请求头字段解读: Referer

  • 链接跳转

  • 正确用途: 推广 , 引流

  • 非法用途: 盗链访问

请求头字段解读: Accept-Language
  • 表示浏览器可以支持的语言类型
    • q是权重系数(0≤q≤1) q越大,请求越倾向于;之前的类型;
    • 未指定默认 q = 1;
    • 若q = 0 提醒服务器不接受该类型.
请求头字段解读: User-Agent
  • 显示浏览器或其他生成该请求的客户端(软件)相关信息.
请求头字段解读: Host
  • 指定出现在被访问的完整URL中主机名称.
  • 若几个web站点以相同的一台服务器为主机,就需要使用Host消息头,因为请求第一行中URL通常不包含主机名称.
请求头字段解读: Cookie
  • 提交服务器向客户端发布的其他参数 识别用户信息
请求头字段解读: Connection
  • 表示持久的客户端与服务连接
    • close: 关闭
    • keep-alive 打开(保持活动)
请求头字段解读: Upgrade-Insecure-Requests
  • 让浏览器自动升级请求,从 http -> https
请求头字段解读: X-Forwarded-For
  • 识别通过http代理或负载均衡方式连接到web服务器的客户端最原始IP地址的字段(包含真实IP)
  • 反向代理,与VPN作用相反

04 请求主体

请求主体只在需要向服务器提交数据时出现，GET 请求没有主体，POST、PUT 请求才有。主体的格式由请求头 Content-Type 声明，服务器依据它选择解析方式。

Content-Type 主体形态 常见场景
application/x-www-form-urlencoded username=admin&password=123，编码方式与 URL 查询串一致 传统表单提交
multipart/form-data 用分隔符 boundary 把各字段与文件拼接在一起 带文件的表单，文件上传
application/json {"username":"admin","password":"123"} 前后端分离项目的接口
  • Content-Length 声明主体的字节长度，服务器依靠它判断主体读到哪里结束
  • 主体的长度不受 URL 长度限制，所以 POST 能提交的数据比 GET 多得多
  • 主体的内容不写入浏览器历史，也不进代理服务器和 Web 服务器的访问日志；但 HTTP 是明文协议，抓包照样能看见
  • 请求头与请求主体之间必须隔一个强制空行，空行之后才是主体内容

1.2 响应(Response)报文

01 报文详解: 响应行/起始行

序号 参考内容 解释说明
01 HTTP/1.1 表示和服务端进行HTTP通讯过程选择的协议版本
02 200 请求结果数字状态码
200是最常用状态码;表示成功提交请求,正在返回请求资源
03 OK “原因” 进一步说明状态

HTTP响应报文中常见状态码:

序号 状态码类型 解释说明
01 1xx 需要提供信息
02 2xx 请求成功处理
03 3xx 客户端被重定向到其它资源
04 4xx 客户端请求包含某种错误
05 5xx 服务端执行请求时遇到错误

状态码信息：100 Continue

  • 当客户端提交⼀个包含主体的请求时，将发送这个响应。
    该响应表示已收到请求消息头，客户端应继续发送主体。请求完成后，再由服务器返回另⼀个响应。

状态码信息： 200 Ok

  • 本状态码表示已成功提交请求，且响应主体中包含请求结果。

状态码信息：201 Created

  • PUT请求的响应返回这个状态码，表示请求已成功提交。

状态码信息：301 Moved Permanently

  • 本状态码将浏览器永久重定向到另外⼀个在Location消息头中指定的URL。以后客户端应使用新URL替换原始URL。

状态码信息：302 Found

  • 本状态码将浏览器暂时重定向到另外⼀个在Location消息头中指定的URL。客户端应在随后的请求中恢复使用原始URL.

状态码信息：304 Not Modified

  • 本状态码指示浏览器使用缓存中保存的所请求资源的副本。服务器使用If-Modified-Since与If-None-Match消息头确定客户端是否拥有最新版本的资源

状态码信息：401 Unauthorized

  • 服务器在许可请求前要求HTTP进行身份验证。WWW-Authenticate消息头详细说明所支持的身份验证类型。

状态码信息：403 Forbidden

  • 本状态码指出，不管是否通过身份验证，禁止任何人访问被请求的资源。

状态码信息：404 Not Found

  • 本状态码表示所请求的资源并不存在。

状态码信息：405 Method Not Allowed

  • 本状态码表示指定的URL不支持请求中使用的方法。例如，如果试图在不支持PUT方法的地方使用该方法，就会收到本状态码。

状态码信息：413 Request Entity Too Large

  • 本状态码表示请求主体过长，服务器无法处理。

状态码信息：414 Request URI Too Long

  • 与前⼀个响应类似，本状态码表示请求中的URL过长，服务器无法处理。

状态码信息：500 Internal Server Error

  • 本状态码表示服务器在执行请求时遇到错误。

    当提交无法预料的输入、在应用程序处理过程中造成无法处理的错误时，通常会收到本状态码。
    应该仔细检查服务器响应的所有内容，了解与错误性质有关的详情。

状态码信息：503 Service Unavailable

  • 本状态码表示尽管Web服务器运转正常，并且能够响应请求，但服务器访问的应用程序还是无法作出响应。应该进行核实，是否因为执行了某种行为而造成这个结果

02 报文详解: 响应头

响应头字段解读: Server
  • 显示web服务器软件
响应头字段解读: Set-Cookie
  • 消息头向浏览器发送另一个Cookie,随后向服务器发送的请求中由Cookie头携带.
响应头字段解读: Pragma
  • 指示浏览器不要将响应保存在缓存中.确保浏览器获取的都是最新内容
响应头字段解读: Content-Type
  • 与请求头Accept对应,表示返回的资源类型
响应头字段解读: Content-Length
  • 规定消息主体的字节长度
响应头字段解读: ETag
  • 验证请求的资源是否发生了改变,如果未改变,则从浏览器缓存中读取,这样就不必再次下载请求.
响应头字段解读: Vary:Accept-Encoding
  • 表示网站一般启用了GZip压缩
响应头字段解读: Expires
  • 作用于网页缓存相关字段,用来控制缓存信息的失效日期

03 响应主体

响应主体是服务器返回的实际内容：HTML 页面、JSON 数据、图片的二进制流、文件下载数据等。它与响应头之间同样隔一个强制空行。

两个与主体直接相关的响应头：Content-Type 说明主体的类型，浏览器据此决定是渲染成页面还是当成文件下载；Content-Length 说明主体的字节数。有些站点把出错页面也返回成 200，这时候判断请求是否失败的依据是主体内容，而不是状态码。

1.3 HTTP协议通讯名词解释

01 URL/URI

URI 是更大的集合，用”协议 + 位置”的方式标注资源的 URL 是它的一个子集。

一个完整 URL 的组成：

部分 作用 示例
scheme 协议 规定访问方式 http、https、ftp
host 主机 域名或 IP 地址 www.example.com、10.0.0.101
port 端口 不写时取协议默认值，http 为 80，https 为 443 :8080
path 资源路径 服务器上的具体资源 /admin/login.php
query 查询串 以 ? 开始，多个参数用 & 连接，参数为 key=value 形式 ?id=1&page=2
fragment 片段 以 # 开始，只在浏览器内部定位，不会发送给服务器 #top
  • 特殊字符要按百分号编码：空格 %20、斜杠 %2F、单引号 %27、井号 %23；不可打印的字节用两位十六进制表示，中文按 UTF-8 编码后逐字节转义
  • 端口和查询串是最先要看的两个位置：非默认端口意味着后面还有另一个服务，查询串是注入类漏洞最常见的落点

02 Cookie

Cookie 是服务器保存在客户端上的一小段数据。响应头 Set-Cookie 下发，之后同一个域下的每次请求都由请求头 Cookie 带回去，服务器靠它认出这是同一个客户端。

Cookie 的常用属性：

属性 作用
Domain 允许携带该 Cookie 的域名，不指定时默认为当前域名
Path 允许携带该 Cookie 的路径，默认为当前目录
Expires / Max-Age 过期时间。两者都不设置就是会话 Cookie，关掉浏览器即失效
Secure 只在 HTTPS 连接上发送
HttpOnly 禁止 JavaScript 通过 document.cookie 读取
SameSite 是否允许跨站请求携带该 Cookie，取值 Strict / Lax / None，用来限制 CSRF
  • 会话 Cookie 与持久 Cookie：关掉浏览器就消失的是会话 Cookie，带 Expires 或 Max-Age 的会写进磁盘，下次打开浏览器还在
  • 浏览器的容量限制大约是每个域名 50 个 Cookie，每个 4KB
  • HttpOnly 只能挡住 JavaScript 直接读取，挡不住 XSS 借浏览器的手替攻击者发请求；会话 Cookie 被窃取后，攻击者不需要账号密码就能接管会话

03 Session

Session 是服务端保存的状态。客户端第一次访问时服务端建一条会话记录并生成 SessionID，通过 Set-Cookie 把 SessionID 发给客户端；后续请求带着这个 ID，服务端在自己的存储（内存、文件、Redis）里找到对应记录，取出登录状态和权限信息。

会话数据放在服务端，客户端手里只有一个不透明的 ID，所以改客户端上的值没有用（除非 ID 可预测，或者服务端校验不严）。

04 Token

Token 是把状态信息本身交给客户端保管的做法，服务端不存会话。最典型的是 JWT：服务端把用户名、过期时间等信息编码进 Token 并签名，客户端在每次请求的 Authorization 头里带上。

  • 服务端只验签名、不查存储，适合多台服务器横向扩展和前后端分离项目
  • Token 通常放在 localStorage 或内存里，由前端代码显式加到请求头上，不再依赖浏览器的 Cookie 机制，因此也不会被浏览器自动携带
  • 代价是签发之后无法直接作废，只能等它过期，或者额外维护一份黑名单

VLAN技术

1.0 VLAN 作用

  • VLAN(虚拟局域网技术)为以太网引入了灵活的控制手段

  • 解决了传统局域网交换机以下问题

    • 安全性差，各个端口之间可以直接互访
    • 效率低，例如广播问题，消耗带宽和CPU资源
    • 业务扩展能力差，设备平等对待每台主机的报文，无法实现差别服务

  • VLAN技术作用

    • 将用户终端分成多个逻辑的网络组 （VLAN 1 VLAN 2 …）
    • 组内可以通讯，组间不允许通讯
    • 二层转发的 单播 组播 广播 报文只能在组内转发
    • 很容易实现对组成员添加，删除

2.0 VLAN 通讯原理

  • 为实现转发控制，在待转发的以太网帧中添加VLAN标记（标记帧 tagged frame）

  • 设定交换机端口对该标记帧进行以下处理

    • 丢弃帧
    • 转发帧
    • 添加标记
    • 移除标记

  • 所有以太网帧在交换机中都以标记帧的形式流动

    • 即某端口从对端设备收到的帧有可能是 untagged frame（非标记帧）

    • 但从本交换机其他端口转发过来的帧一定是 tagged frame

    • 若收到 tagged frame 则进行转发

    • 若收到 untagged frame 则必须加标记 => (untagged => tagged)

  • VLAN 编号范围 04095 其中0和4095预留 实际:14094可用

3.0 VLAN 接口类型

  • Access 接口

    • 仅允许VLAN ID与接口的PVID相同数据帧通过
    • 接口收到设备发送帧为untagged，交换机强制对数据帧添加该接口的PVID
    • 接口发往对应主机的以太网帧永远是untagged
    • 多数交换机默认 接口类型是Access PVID = 1，VLAN 1由系统创建，不能被删除

  • Trunk 隧道接口类型 （用于连接交换机）

    • 交换机之间传输标记帧，可自由设定允许通过多个VLAN ID ID可以与PVID相同，也可不同
    • 若标记帧的VLAN ID 未配置，则丢弃帧

网络通讯协议—TCP协议原理

1.0 概述

TCP协议全称（传输控制协议）一种面向连接的、可靠的、基于字节流的传输层通信协议；

为实现面向连接，在发送数据之前必须在两端建立连接，方法是“三次握手”；

为保证可靠性，则需TCP报文中的段编号以及确认号。

简单来说就是给每个包一个序号，序号保证了传输到接收端的数据包是按顺序接收；

接收端成功接收到字节则回复一个(ACK)；

1.0.1 TCP报文结构：

1.0.2 报文重点信息说明：

  • Source Port Number [源端口]

    字段说明：（占用16bits，即2byte）

    表示网络访问来源处的端口号，指定了发送端的传输层协议端口信息（一般是随机生成）

  • Destination Port Number [目标端口]

    字段说明：（占用16bits，即2byte）

    表示网络访问目的处的端口号；即指定了接受端的传输层协议端口信息（根据访问的服务进行指定）

引申：通过以上信息不难发现，源/目标端口均占用16bits，因此可以通过计算得知其端口号范围

2^16 = 65536 （端口号数量 = 65536）

最大端口号 = 65535 端口号范围 0~65535

其中 0 号端口一般不使用，0~1023 端口是知名端口（例如HTTP 80），已经被占用。

  • Sequence Number [序列号]

    字段说明：（占用32bits 4字节）

    每一个TCP报文段都会有一个序列号，序列号字段的值其实是本报文段所发送的数据的第一个字节的序号。

    这是因为TCP是面向连接的可靠服务，其每一个字节都会对应一个序号，通过序号来确保服务的可靠性和有序性。

  • Acknowledgement Number [确认号]

    字段说明：（占用32bit，即4字节）

    确认号，是期望收到对方的下一个报文段的数据的第一个字节的序列号，可以有效核实传输的数据是否准确。

  • SYN 字段

    字段置为1时，表示发送方请求和接收方建立连接

  • FIN 字段

    字段设置为1时，表示某一方请求和对方断开连接

  • ACK 字段

    ACK标志位为1时，表示本报文中的“确认号”字段有意义。通常除第一个SYN报文外，所有TCP报文都将ACK置1。

    ACK = 1 使 ack = x+1 生效，它告诉对方：我已经收到 seq = x 的数据，请你接下来发送 seq = x+1 的数据给我。

2.0 TCP通讯原理

2.0.1 三次握手—通讯建立

  • 第一次握手 Host A ==> Host B

    Host A 向 Host B发送建立TCP连接请求的报文。

    SYN = 1, seq = x (注意：此时的序列号是随机生成)

  • 第二次握手 Host B ==> Host A

    Host B 向 Host A 回复，已经收到Host A发送的TCP连接请求报文。

    ACK = 1, SYN = 1, seq = y, ack = x + 1

  • 第三次握手 Host A ==> Host B

    Host A 向 Host B 回复，已经收到Host B发送的TCP连接请求报文。

    ACK = 1, seq = x + 1, ack = y + 1

    经过以上三次握手过程，两台主机已经建立完整可靠的TCP连接。

2.0.2 四次挥手—通讯断开

  • 第一次挥手 Host A ==> Host B

    Host A 向 Host B发送断开TCP连接请求报文。

    FIN = 1, ACK = 1, seq = 101, ack = 301 （假设此时两台主机传输报文序列号为：101，301）

  • 第二次挥手 Host B ==> Host A

    Host B接收到Host A发送的断开连接请求报文。

    ACK = 1, seq = 301, ack = 102

  • 第三次挥手 Host B ==> Host A

    Host B向Host A发送断开连接请求报文。

    FIN = 1, ACK = 1, seq = 301, ack = 102

  • 第四次挥手 Host A ==> Host B

    Host A向Host B回复最后一次断开TCP连接请求报文

    ACK = 1, seq = 102, ack = 302

    经过以上四次挥手过程，TCP连接成功断开。
