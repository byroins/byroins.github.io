00 危害

危害 说明 证据
认证绕过 / 未授权访问后台 无需任何账号密码，直接取得后台身份（本次为 id=1 超管） 5 个后台页 302 → 200

02 换思路，构造”字符串身份”

  • 目的：验证”服务端是否真的会把我们塞的对象当成身份”。

  • 原理：载荷 = SimplePrincipalCollection（Shiro 自带容器）+ 一个字符串。
    字符串是本地必然存在的类，因此一定能被反序列化，用来做”通行对照”。

  • 操作：用密钥加密该载荷，得到 cookie，访问 /admin：

  • 结果：
请求 状态码 deleteMe
无 cookie 302 → /login 无
字符串身份 500 无
错误密钥 302 → /login 有
  • 判断
  1. deleteMe 消失 ⇒ 密钥正确、服务端解开了并反序列化成功；
  2. 状态码从 302 变成 500 ⇒ 请求已经被放行到业务代码（过滤器被绕过）；
  3. 500 的原因 = 业务代码要把 principal 强转成它自己的用户类，而我们是 String，转不过去。

  • 目的：不用猜产品，直接从目标自己吐的信息里拿。

  • 操作：访问 Druid 的运行时信息接口 /druid/basic.json。

  • 实测结果（关键字段）：

    另可见 Druid 1.1.10、数据库驱动 com.mysql.cj.jdbc.Driver。

  • 判据：

    • JavaClassPath = 部署包名 ⇒ 目标就是开源产品 Webstack-Guns（对应其 GitHub 源码）；
    • JavaVersion 1.8.0_231 ⇒ JDK 8（这解释了为什么经典 gadget 理论上应可用，RCE 失败更可能是链/回显适配问题，而不是 JDK 限制）。

05 定位”身份类”的类名与字段

  • 目的：拿到目标期望的 User 类的全限定名与字段清单。

  • 操作：按包名去 GitHub 读该产品源码（ShiroConfig / ShiroUser / 过滤器配置）。

  • 实测结果：该产品有多个分支，每个分支的包名不同，字段基本一致：

    分支 用户类全限定名
    分支一 com.jsnjfz.manage.core.shiro.ShiroUser
    分支二 com.nikati.manage.core.shiro.ShiroUser

    字段（两者相同）：id / account / name / deptId / roleList / deptName / roleNames，
    且 implements Serializable、未显式声明 serialVersionUID（即按字段结构计算出 UID，通常与 1L 一致）。

  • 判据：

    • 类名必须与目标一字不差 —— 类不在目标 classpath 上 ⇒ ClassNotFoundException ⇒ deleteMe；
    • 产品分多个分支 ⇒ 无法从外观判断 ⇒ 只能盲测（各造一张卡试一次）。

07 修复建议

  1. 轮换 cipherKey 为随机值（取消使用任何公开字典里的默认键）；
  2. 不需要 rememberMe 功能可关（setRememberMeManager(null)），从根源关闭客户端可控反序列化；
  3. 升级 Apache Shiro 到已修复版本，并核对 1.2.5 之后的所有相关 CVE；
  4. 启用 JEP 290 反序列化过滤器（白名单） —— 即使密钥再次泄漏，也能阻断反序列化利用；
  5. 收敛敏感端点：Druid 监控台 / Swagger 不应对外网开放，且需加认证。

检测 / 排查

  1. 排查历史日志中的 Shiro 反序列化异常与异常长度的 rememberMe cookie；
  2. WAF 可对”超长 rememberMe + 异常请求头”组合做拦截。
