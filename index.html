1.0 中间件安全

1.1 什么是中间件?

中间件(Middleware) 是指一种软件组件, 作用是在不同系统, 应用程序或服务之间传递数据和消息, 通常位于应用程序和操作系统之间, 负责在不同的应用程序之间传递数据, 协调不同应用程序之间的通信, 以及处理网络请求等.

中间件通常是插件式架构, 允许被集成到现有应用程序中, 可提供如: 身份验证, 授权, 缓存, 负载均衡, 日志记录, 安全性等功能, 以求简化应用程序的开发和部署过程.

  • 广义: 涵盖了从web服务器到身份验证系统, 再到消息传递等一切内容
  • 具体: Jboss Weblogic Tomcat Apache等

1.2 中间件漏洞

中间件漏洞是指在中间件软件中存在的安全漏洞, 通常包含以下几种:

  1. 代码注入漏洞: 向中间件发送恶意代码, 执行任意代码或获取敏感数据;
  2. 跨站脚本漏洞: 在中间件输出的网页中插入恶意脚本, 来窃取用户信息或进行其他恶意行为;
  3. SQL注入漏洞: 对中间件输入的SQL查询中插入恶意代码, 执行任意SQL查询或获取敏感数据;
  4. 认证和授权漏洞: 攻击者可以利用中间件的认证和授权机制的漏洞, 来绕过访问控制, 获取系统权限;
  5. 文件包含漏洞: 攻击者可以利用中间件的文件包含功能, 来包含恶意文件并执行任意代码.

2.0 Tomcat

Tomcat是一个开源的Java Servlet容器, 由Apache软件基金会开发, 它可以作为独立的Web服务器或应用服务器, 也可以作为其他Web服务器的插件来使用, 如Apache HTTP Server.

Tomcat支持Java Servlet, JavaServer Pages(JSP), Java Expression Language(EL)和WebSocket等Java技术, 并提供了许多企业级特性, 如集群, 安全性和可扩展性.

03 WAR包部署

WAR(Web Application Archive) 是一种Web应用程序的打包格式, 用于将Web应用程序打包成一个单独的文件, 便于部署和分发. WAR文件实际上是一种JAR(Java Archive)文件, 其中包含了Web应用程序的全部内容, 包括Java类, HTML, JSP, Servlet, XML配置文件, 静态资源 (如图片, CSS, JavaScript文件等). WAR文件还可以包含一些特定Web应用程序的配置文件, 例如web.xml, context.xml等.

WAR文件通常是通过Web服务器部署的, 例如Tomcat, Jetty等. 在部署Web应用程序时, Web服务器会将WAR文件解压缩并将其部署到指定的目录中, 然后启动Web应用程序. 通过将Web应用程序打包成WAR文件, 可以方便地将应用程序部署到不同的Web服务器中, 也可以方便地将应用程序分发给其他人使用.

1.0 PHP 反序列化

1.1 基础

序列化是将内存中的对象转换为字节序列或字符串的过程, 以便于存储, 传输或在网络传递.

反序列化则是将字节序列或字符串还原为原始对象.

漏洞原理: 反序列化漏洞的本质: 攻击者可控的恶意数据被程序信任并还原为对象, 而程序未对输入进行严格验证.

  • 反序列化特性:
    • 反序列化生成的对象, 成员属性值由被反序列化的字符串决定, 与原来类预定义的值无关
    • 反序列化使用unserialize() 将字符串转换为对象, 序列化使用serialize() 将对象转化为字符串
    • 反序列化不触发类的成员方法, 需要调用方法后才能触发

1.0 JWT基础

1.1 什么是JWT?

定义:

JWT (JSON Web Token) 是一个开放标准, 定义了一种紧凑且自包含的方式, 用于在各方之间以 JSON 对象的形式安全传输信息. 令牌本身包含了所有必要的用户信息, 服务端无需额外存储会话状态

特点:

  • 紧凑: 体积小, 适合通过URL, POST 参数, HTTP Header 传递
  • 自包含: 携带用户ID, 角色等关键信息, 减少数据库查询
  • 跨域: 天然支持跨域认证, 适合微服务和前后端分离架构

核心应用场景

场景 说明
认证 用户登录后, 后续请求携带 JWT 即可访问受保护资源
信息交换 使用公钥/私钥对签名, 确保发送方身份可信

1.2 JWT 与 Session的区别(为什么需要 JWT?)

传统 Session 认证问题:

  • 服务端需要存储 Session, 分布式环境下需共享存储(如Redis), 增加复杂度
  • 存在单点故障风险
  • 扩展性受限, 新增服务实例需同步认证状态

JWT 的无状态优势:

详见 特点

1.3 JWT 核心结构

一个完整的 JWT 由三部分组成, 用点号分隔 '.'

01 Header (头部)

描述 JWT 的元数据, 是一个 Base64Url 编码的 JSON对象

alg 字段指定签名算法, typ 固定为JWT

02 Payload (荷载)

JWT 的主体内容, 包含需要传递的声明

注册声明(Registered Claims) – 预定义的标准字段

声明 全称 含义
iss Issuer 签发者
exp Expiration Time 过期时间(必须使用Unix时间戳)
sub Subject 主题(通常为用户ID)
aud Audience 受众
nbf Not Before 在此时间之前不可用
iat Issued At 签发时间
jti JWT ID JWT 唯一标识

公共声明(Public Claims) : 自定义字段, 用于传递非敏感信息, 如用户ID, 角色.

私有声明(Private Claims): 双方约定的自定义信息.

重点: Payload 仅 Base64 编码, 不是加密, 任何能拿到Token的人都可解码读取内容.

03 SIgnature (签名)

对 Header 和 Payload 进行签名, 用于验证令牌的完整性和真实性.

HS256 对称签名

两种主流签名算法对比:

算法 类型 特点 场景
HS256 对称加密 同一密钥签名和验证, 密钥不能泄露 单一服务端内部使用
RS256 非对称加密 私钥签名, 公钥认证 分布式系统, 第三方验证

1.4 JWT 工作原理

以下 JWT 验证流程图解

流程:

  1. 用户登录: 客户端向服务端发送用户名和密码
  2. 服务器验证: 验证凭据是否正确
  3. 生成 JWT: 使用密钥签名, 编码用户信息(如 ID, Role) 和过期时间
  4. 返回客户端: 将 JWT 返回给客户端
  5. 客户端存储: 通常存储在localStorage或 Cookie中
  6. 携带 JWT 请求: 后续请求在Authorization: Bearer <JWT>Header中携带
  7. 服务器验证: 验证签名和有效期, 通过则允许访问

2.0 JWT 常见漏洞与攻击手法

  • alg: none 攻击

    将 Header 中的alg改为none, 并删除签名. 部分有缺陷的库会直接接受未签名的Token

    • 影响: 完全绕过身份验证, 可伪造任意用户身份

    • 利用: jwt_tool -X a

  • 算法混淆攻击(RS256 → HS256)

    利用非对称加密 (RS256) 和对称加密 (HS256) 的差异, 攻击者获取公钥后, 将其作为 HMAC 的 “密钥” 伪造Token

    原理: 服务端期望 RS256 验证, 但攻击者将算法改为 HS256, 用公钥作为对称密钥签名.

  • 弱密钥爆破

    如果 JWT 使用 HS256 且密钥太弱 , 可用社工字典暴力破解.

  • kid 参数注入

    kid (Key ID) 用于指示服务器使用哪把密钥验证, 若输入过滤不严, 可进行:

    • 路径遍历: ../../dev/null (使服务器使用空密钥)
    • SQL注入: 操纵密钥查询逻辑

  • jku (JWK Set URL) 注入

    jku 告诉服务器去哪里获取公钥, 若服务器未校验该URL, 攻击者可将其指向自己控制的服务器, 用自己生成的密钥伪造Token

  • 信息泄露

    Payload 仅 Base64 编码, 不是加密, 攻击者可轻易解码读取其中的敏感信息

1.0 CSRF (跨站请求伪造)

01 定义:

CSRF, 攻击者诱导已登录的用户在不知情情况下执行非本意操作, 完成恶意请求

  • 利用 Web 应用的身份验证机制和会话管理机制的固有缺陷:
    • 服务器无法区分请求是用户主动发起, 或用户被动触发
    • 请求携带有效的 Session Cookie, 服务器认为”合法”

02 漏洞成因

  • 浏览器会自动携带目标站点Cookie发起跨站请求, 服务端仅靠Cookie/Session做身份校验, 不能保证请求是否由用户本人主动发起.
  • 常见缺失防御:
    • 未校验 CSRF-Token;
    • 未校验 Referer / Origin 请求头;
    • 关键业务接口无二次身份校验.

03 攻击流程

以下 CSRF 攻击链逻辑图解

04 CSRF 三要素

  • 目标操作: 存在可被请求直接触发的业务接口(修改信息, 转账, 修改密码)
  • 会话依赖Cookie: 浏览器自动带上Cookie, 服务端仅凭Cookie识别用户身份
  • 请求参数可控: 接口请求参数可被攻击者完全预知, 构造, 无随机不可预测的校验 Token

注意: CSRF不能获取 Cookie, 不能读取响应, 只能借用受害者身份执行操作.

1.1 同源策略

01 定义:

同源策略指在 web 浏览器中, 允许某个网页脚本访问另一个网页的数据, 但前提是两个网页必须同源, 不同源的客户端脚本在没有明确授权的情况下, 不能读写对方的资源, 如Cookie, 同源策略 是浏览器安全模型, W3C标准规范

  • web应用程序广泛依赖于Cookie维持会话, 所以必须将不相关网站严格分隔, 防止数据泄露

02 案例

同源策略 需要对比两者域名(host), 端口, 协议, 三者完全相同即同源.

案例: 与http://www.example.com/index/index.php比较

源 是否同源 原因
http://test.example.com/admin/index.php 否 域名不同
https://test.example.com/admin/index.php 否 协议不同
http://test.example.com:8080/admin/index.php 否 端口不同
http://www.example.com/test/index.php 是 同源策略

03 核心

  • 同源策略不会阻止表单, img , script, iframe, link等标签发起跨站请求, 只阻止 JS 读取跨站返回结果, 这正是CSRF 能够生效的底层原理: 浏览器可以跨域发请求, 自动带上 Cookie, 只是 JS 拿不到返回包

1.0 SSRF (服务端请求伪造)

1.1 基础

  • 客户端请求:

    由客户端设备(个人计算机, 手机, 平板电脑) 或软件 (浏览器, 各种APP) 发出的请求, 以获取指定的网页, 图片, 视频或其他资源, 例: 用户在浏览器输入URL或点击链接时, 浏览器会自动发起HTTP请求, 请求服务器返回指定资源.

  • 服务端请求

    服务器应用程序或服务会提供功能接口, 比如API接口, 用于与其他服务进行数据交互, 这些由服务器之间的请求称之为服务端请求.

1.2 什么是SSRF

SSRF(Server-Side Request Forgery, 服务端请求伪造): 服务器在没有对目标地址做有效过滤的情况下, 替攻击者向任意地址发起请求, 攻击者相当于把服务器当成了”跳板机”, 攻击者使用受害者服务器应用程序作为代理, 让请求拥有服务器特征.

SSRF 漏洞核心标准:

  • 请求是否由服务器发起

  • 如何判断请求是否由服务器发起?

    • 有回显: 是否可以探测到内部服务?
    • 无回显: 由访问IP判断

以下 SSRF 攻击链逻辑图解

1.3 漏洞成因

由于服务端提供从其他服务器应用获取数据的功能, 但又未对目标地址做严格过滤与限制, 导致攻击者可以传入任意地址让后端服务器对其发起请求, 并返回请求数据, 例: 从指定URL获取网页文本内容, 加载指定地址的图片, 下载等…

1.4 漏洞危害

  • 窃取数据: 攻击者可伪造请求以访问服务器内部网络或云环境中的其他服务或资源
  • 攻击第三方系统: 攻击者可伪造请求攻击第三方系统, 例: 访问其他组织敏感数据或执行拒绝服务攻击
  • 内部端口扫描: 攻击者可伪造请求扫描服务器内部端口和服务
  • 获取指纹: 通过获取 web 应用收集指纹信息
危害 说明 典型 payload 协议
读服务器本地文件 读 /etc/passwd、win.ini file://
内网端口扫描 / 服务探测 扫存活主机、探测 Redis/MySQL http://、dict://
攻击内网未授权服务 打 Redis 写 webshell → RCE gopher://
云凭据窃取 偷 AWS/阿里云 IAM 临时凭据 http://169.254.169.254

协议就是 SSRF 的武器库: file 读文件、dict 探服务、gopher 发任意 TCP 字节流(万能)

1.5 漏洞场景

SSRF 漏洞一般存在于 Web 应用程序中, 应用程序接收来自用户的输入, 将请求转发至其他服务器, 攻击者在输入中注入恶意URL, 使服务器发起未授权请求, 访问敏感内部资源.

  • 文件上传功能
  • 图片处理功能
  • URL重定向
  • API调用

1.4 修复防范

  • 数据输入验证

    • 对用户提交的文件路径参数进行严格的格式检查和白名单策略, 只允许包含预定义的, 安全的文件路径
    • 禁止包含绝对路径, 转而使用相对路径, 并且确保相对路径不会超出预期的目录范围

  • 禁用危险函数或配置

    • 如果不是必须, 尽量避免使用容易导致文件包含漏洞的函数, 如PHP中的allow_url_include配置项应设为Off以禁用远程文件包含
    • 在php.ini配置文件中, 可以设置open_basedir限制PHP脚本只能访问指定目录及其子目录下的文件

  • 使用安全函数

    • 使用更安全的函数替代易出问题的文件包含函数, 例如在PHP中, 可以使用readfile()配合自定义的文件路径处理逻辑来代替include()

  • 错误处理与日志记录

    • 正确处理文件包含失败的情况, 不要暴露过多的错误信息, 以免给攻击者提供有用的信息
    • 记录详细的日志, 以便在发生异常时追溯分析问题

01 文件上传漏洞是什么?

文件上传漏洞是指攻击者上传了一个可执行的文件到服务器并成功执行, 从而获取服务器权限的漏洞. 其本质是服务端未对上传文件进行充分校验, 导致恶意文件(如 WebShell)被当作合法文件存储并解析执行.
