Hermes-PentestAgent

Posted on 2026-10-01 Edited on 2026-10-15 In project , Hermes-PentestAgent

摘要

大语言模型（LLM）应用于渗透测试时面临四个结构性障碍：执行过程不可控、结论不可复现、证据不可审计，以及模型自身不可验证。现有自动化工具以漏洞发现率为主要目标，未对授权边界与证据留存提供机制性保障；通用智能体框架虽具备自主决策能力，却缺少对测试范围的强制约束与对执行过程的完整记录。本文提出 Hermes-PentestAgent，一个受控的 AI 渗透测试编排框架。该框架由决策层（Hermes Agent）、方法层（技能库）与执行层（Kali Linux）三个组件构成，并在组件之上引入三层自研结构，本文分别命名为契约层、边界层与证据层：契约层由 Agent 侧规范与项目级授权声明共同约束工作方式，边界层以单一事实来源固化授权范围，证据层要求原始输出在执行当下落盘、且所有结论均可回溯。

框架在授权环境中完成第一阶段验证：信息收集阶段测绘出漏洞模块 59 个、含参数端点 38 个；两个阶段共生成证据文件 24 个；漏洞验证阶段确认漏洞 28 项（Critical 9、High 6、Medium 13），评分依 CVSS 3.1 官方公式程序计算。结果表明，该框架能够在保证过程可审计的前提下完成完整的渗透测试流程；模型能力方面，报告全部结论均可回指证据文件，未发现无证据支撑的判断。依合规要求，目标环境的具体标识不在本文披露。

关键词：渗透测试；大语言模型；智能体；授权边界；可审计性；模型评估；CVSS

1.0 引言

1.1 研究背景

渗透测试是评估目标系统安全性的重要手段，其流程已高度成熟。OWASP WSTG、PTES 与 NIST SP 800-115 等标准均给出了从信息收集到漏洞验证、再到报告输出的完整方法论[1-3]。

但方法论成熟并不等同于执行高效。一个完整的 Web 应用测试通常需要：对每个端点完成多次探测，并依据响应逐层修正判断；保存、归类每次工具调用的原始输出并建立索引；在报告中把每一条结论回溯到具体证据。

上述工作中，判断依赖经验，而记录与整理属于重复劳动。这正是大语言模型可以介入的位置。

1.2 问题定义

将 LLM 直接用于渗透测试，最直观的形式是：把目标信息交给模型，由模型自行选择并执行命令，最终输出结论。该形式在工程上存在四个结构性障碍，前三个属于流程侧，第四个属于模型侧。

（1）不可控。模型对命令序列的决策缺少外部约束，可能执行超出授权范围的探测，或触发具有破坏性的操作。

（2）不可复现。结论依赖于单次会话的上下文，缺少可独立验证的执行记录；模型或会话一旦变更，结论即发生漂移。

（3）不可审计。结论以自然语言给出，却不附带原始证据。在客户评审、漏洞平台审核或技术面试中，评审方通常追问发现路径，而缺少证据的结论无法回答该问题。

（4）模型不可验证。前三项约束均作用于流程，而流程的执行者仍是模型。若模型本身会产生臆造——以”一般来说””通常”一类表述填补未探测的空缺，或给出无法回指输出的结论——则约束只能抑制、不能消除该风险。因此框架设计必须一并回答：对模型可靠性的验证如何进行。

四项之中，第（3）项最为关键——渗透测试交付的是结论，而结论的价值由其证据质量决定。 第（4）项则决定这一价值能被信任到什么程度。

1.3 本文工作

Hermes-PentestAgent 将 LLM 定位为执行环节的替代者：

  • 方法论由既有技能库提供，避免模型即席构造流程；
  • 决策由 Agent 完成，包括阅读输出、判断下一步、标注异常；
  • 执行落在真实工具链上，基于 Kali Linux；
  • 约束由契约层强制，覆盖授权范围、禁止动作与证据留存。

系统的核心不在上述组件本身，而在组件之上的三层结构——契约层、边界层与证据层。组件可替换，而这三层决定了框架能否回答以下问题：授权范围以何为据、如何保证不越界、结论依据何在。

相应地，本文的评估也分为两部分：渗透结果（测绘规模、漏洞确认、证据完整性）与模型能力（幻觉控制、工具调用质量、可复现性）。前者验证流程机制是否生效，后者验证执行者是否可靠（1.2 节第（4）项）。两部分的结果分别在 5.2–5.5 节与 5.6 节给出。

2.0 相关工作

2.1 自动化漏洞扫描

以 AWVS、nuclei、xray 为代表的扫描器依赖预定义规则或 PoC 模板，具备高吞吐与低误报的优点。但其检测范围受限于既有规则，难以处理需要多步推理与上下文关联的场景，且不产生可追溯的判断过程。

2.2 渗透测试方法论标准

OWASP WSTG、PTES 与 NIST SP 800-115 等标准给出了规范的阶段划分与检查项[1-3]。这类标准解决”做什么”的问题，但不提供自动化执行能力，仍需人工逐项落实。

2.3 基于 LLM 的智能体框架

通用智能体框架提供工具调用、多轮规划与上下文管理能力，自主性较高。但其设计目标是通用任务的完成度，缺少渗透测试所需的三项约束：授权范围的单一事实来源、范围外操作的强制拒绝、执行过程的强制留痕。

2.4 LLM 智能体的治理控制与评估基准

与本文约束机制直接相关的，是 LLM 智能体治理领域对控制项的三类划分：design（设计期）、runtime（运行期）、audit（审计期）。多数治理框架按此划分组织控制项，但普遍停留在原则层面，未给出与具体业务对象（授权范围、目标主机、证据文件）的耦合方式。

在机制一侧，访问控制领域已有更具体的划分。NIST SP 800-207 零信任架构区分策略判定点（Policy Decision Point, PDP） 与策略执行点（Policy Enforcement Point, PEP）：前者判定请求是否合规，后者在数据通路上执行该判定[5]。将同一思路引入智能体授权的尝试也已出现，IETF 的 Agent 交互与委派协议草案将”执行边界（Execution Boundary）”定义为”负责执行授权、执行动作并产出记录的组件”。

在评估一侧，已有工作为渗透测试智能体建立了可复现基准，并给出了若干可直接引用的实测结果：

  • AutoPenBench 提供 33 个难度递增的脆弱系统任务，并区分完全自主与半自主两种架构[6]。实测结果：完全自主成功率 21%（简单任务 27%，真实世界任务仅完成 1 个），而同一基准下引入人工交互的半自主架构达 64%——后者为前者的三倍，说明人工介入在渗透测试任务上并非可选项。
  • Pentest-R1 经两阶段强化学习微调后，在 AutoPenBench 上达 24.2%，仅次于 Gemini 2.5 Flash；在 Cybench 的无引导任务上为 15.0%[9]。
  • PentestEval 按六个阶段（信息收集、弱点汇集与筛选、攻击决策、利用生成与修正）评测 9 个主流模型，涵盖 GPT-3.5-turbo、GPT-4o、GPT-4o-Mini、GPT-OSS-120b、Qwen-Plus、Qwen-Max、DeepSeek-V3、DeepSeek-R1 与 Claude-3.7，覆盖 346 个任务与 12 个真实脆弱场景[10]。结果显示端到端流程成功率仅 31%，多数阶段低于 50%，其中攻击决策阶段最弱。
  • AutoPentest-Bench 面向 IP-to-Root 全自主流程，并在 10 个 LLM 上做了探索性研究[7]。
  • IETF BMWG 的 AI Agent 安全评估基准草案给出 4 个一级维度与 55 个二级指标，并将 Agent 的生命周期风险划分为感知、记忆、决策、执行四类[8]。

需要强调：以上均为公开基准在各自任务集上对通用模型的评测结果，与本文框架的任务集及判定标准均不相同，因此仅作参照，不构成同条件对比。

这些结果对本框架有两重意义：其一，完全自主在渗透测试上并不成立，这为本文的人机放行设计（4.3 节）提供了外部依据；其二，评估对象应同时覆盖模型能力与流程约束，本文据此把评估拆为渗透结果（5.2–5.5 节）与模型能力（5.6 节）两部分。

2.5 小结

现有工作或缺少推理能力（2.1），或缺少自动化能力（2.2），或缺少面向合规的约束与留痕机制（2.3）。治理与零信任领域（2.4）提供了机制层面的参照，但其对象是通用的访问请求，而非渗透测试的授权范围与证据；已有的智能体基准（2.4）度量了任务成功率，却未把授权边界与证据留存纳入评价维度。

本文的工作位于三者交叉处：保留 LLM 的推理与归纳能力，同时通过结构化的约束与证据机制，使其满足渗透测试对可控性与可审计性的要求，并将评估拆分为渗透结果与模型能力两部分。

3.0 系统设计

3.1 设计目标

  • 方法论可审查：每一阶段的执行依据可指认到具体流程来源；
  • 结论可回溯：报告中的每条结论均可定位到原始输出；
  • 边界可强制：授权范围有唯一来源，范围外操作被拒绝；
  • 决策可干预：阶段之间由人放行，模型不自主跨越阶段。

3.2 总体架构

系统由三个组件层与三个自研层构成，如图 1 所示。

三个组件均为既有能力：Hermes Agent 负责决策与编排，Skills 负责提供方法论，Kali Linux 负责执行。框架的自研部分位于组件之上的三层结构。

关于术语来源。 三个组件层的命名沿用通用表述；而自研的三层是本框架为便于表述所作的命名，并非既有标准用语。其各自对应的既有概念如下，后文沿用本文命名：

本文命名 对应既有概念 出处
契约层 Guardrails / Policy——对模型行为的规范化约束 OWASP LLM Top 10；NVIDIA NeMo Guardrails
边界层 Policy Enforcement Point（PEP）/ Trust Boundary NIST SP 800-207[5]；IETF AIDP 草案的 “Execution Boundary”
证据层 Audit Trail / Provenance / Chain of Custody 取证与合规领域通用概念

三层与 2.4 节所述的 design / runtime / audit 三类控制在职能上一致：契约层对应设计期约束，边界层对应运行期约束，证据层对应审计期约束。本文的区别在于将三者显式耦合到渗透测试的具体对象上——授权范围、目标主机与证据文件——而非停留在原则层面。

3.3 契约层

契约层（对应 design 期的 guardrails 类约束）由两个文件共同承担。二者作用域不同、职责互补：

文件 作用域 加载方式 承载
SOUL.md Agent 身份（profile 级） 每次会话自动注入 方法、落盘规范、红线
AGENTS.md 项目级 从当前工作目录自动加载 项目根锚点、授权依据、禁止项

拆成两个文件的依据是二者的作用域不同：

  • 方法是跨项目成立的。”原始输出先落盘再归纳””先方案后执行”在任何渗透项目中都适用，因此归入 Agent 侧规范。
  • 授权是逐项目的事实。”本项目已授权”必须绑定到具体项目。若写入 Agent 侧规范，则该 Agent 在任何目录、任何会话中都会携带”已授权”这一前提，边界随即失效。

AGENTS.md 从当前工作目录被自动加载，因而其作用域与项目作用域天然对齐：在项目目录内启动会话即受其约束，在其它目录则不受影响。

Agent 侧规范的内容结构：

  1. 角色定位；
  2. 红线——授权优先、证据优先、绝不臆造、危险动作先问、先方案后执行；
  3. 方法与落盘规范——技能选取、阶段确认、原始输出与报告的落盘位置及命名；
  4. 风格。

其中”绝不臆造”一项值得说明：它禁止模型以”一般来说””通常”一类表述填补空缺，从而抑制臆测在报告中的传播。

3.4 边界层

边界层（即零信任架构中的策略执行点）由 scope.json 承担，作为授权范围的单一事实来源：

设计要点有四：

  1. allowed 为白名单语义——未列出的目标一律不测试；
  2. never 的优先级高于 allowed；
  3. 目标带 type 字段（web / ip / cidr），使校验程序能按类型分别处理——CIDR 尤其不能被当作 URL 路径切分，否则 192.0.2.0/24 会退化为单个地址而被误判为”在范围内”；
  4. 人与 Agent 读取同一文件，排除”口头授权”与”上下文记忆”作为授权依据。

其中 authorization 块是本设计的关键：它记录授权的来源、对象、效力依据与有效期。

这一块的作用是把”自证”变成”引用”——Agent 无法核验授权的真伪，但可以核验”是否填写了依据”。授权依据为空、或无法指向可核验来源时，框架要求立即停止，不得进入任何主动测试阶段。

缺少该块时，allowed 退化为一份任意清单：任何被填入其中的目标都会被视为”已授权”，边界层随之失效。

3.5 证据层

证据层（对应 audit 期的 audit trail）由 evidence/ 与 notes/ 两个目录构成，职责不同：

  • evidence/ 存放工具原始输出，命名格式为 <YYYYMMDD>-<HHMMSS>-<工具>.txt，写入后不再修改；
  • notes/ 存放归纳结论，其中每一条结论均需指向对应的 evidence 文件。

时间戳前缀使证据目录天然按时间排序，任一第三方可在无额外说明的情况下复原执行时间线。此外，范围变更同样作为证据落盘（见 5.2 节），保证授权状态的变更过程可查。

3.6 执行流程

一次完整执行按以下步骤进行：

  1. 依 Agent 侧规范确认工作方式，读取 AGENTS.md 确认项目根与授权依据；
  2. 读取 scope.json，确认授权目标；
  3. 加载对应阶段的技能，取得该阶段的方法与步骤顺序；
  4. 经 SSH 在 Kali 上执行真实工具；
  5. 原始输出立即落盘至 evidence/；
  6. Agent 阅读输出，完成归纳、标注阴性结果并给出下一步建议；
  7. 由人确认后进入下一阶段；
  8. 全部阶段结束后生成 notes/ 报告，结论逐条可回指证据文件。

其中第 5 步与第 8 步为关键约束：证据在执行当下产生，而非事后补录。

4.0 实现

4.1 组件选型

组件 角色 选型依据
Hermes Agent 决策与编排 具备工具调用、多轮上下文与本地文件读写能力
Cybersecurity-Skills 方法论 可将成熟流程固化为可加载的步骤
Kali Linux 执行 工具链完整，与生产测试环境一致

4.2 项目目录与作用域

项目目录保持最小化，仅包含四类内容：

Agent 本体（Agent 侧规范、Skills、会话状态）位于 Hermes 的工作目录下，不纳入项目目录。依据：Agent 属于工具，而证据、报告与范围定义属于项目资产，二者的生命周期与共享范围不同。

因此契约层横跨两处：规范随 Agent 走，授权随项目走。

4.3 阶段划分与人机协同

测试被划分为若干阶段（信息收集、漏洞验证、报告输出），阶段之间设置人工放行点。设计依据：

  1. 技术层面——信息收集基本无副作用，而漏洞验证可能改变目标状态，二者风险等级不同；
  2. 责任层面——授权由人给出、风险由人承担，因此阶段推进的决策权亦应在人一侧。

放行采用固定流程：复述范围 → 提出方案 → 人工确认 → 执行并归纳。

该设计有外部依据。AutoPenBench 的实测显示，完全自主的智能体在 33 个渗透任务上的整体成功率仅 21%，真实场景任务仅完成 1 个；而同一基准下引入人工交互的半自主架构成功率达 64%，为前者的三倍[6]。这与本文的判断一致：在渗透测试这类高风险、长链路、步骤间强依赖的任务上，人的介入不是效率损失，而是必要条件。

5.6.2 指标设计原则

指标定义遵循两条原则：

  1. 可判定——每条指标都必须能被第三方依据落盘证据重新计算，不接受主观评分；

其中幻觉率的定义值得说明：本文不采用”模型输出是否错误”这一宽口径，而采用”结论能否在证据文件中找到支撑“这一窄口径。理由有二：其一，后者可判定、可复核；其二，报告的每条结论本就要求回指证据文件（3.5 节），因此该指标可由现有材料直接计算，无需额外标注。

5.6.5 结论的边界

上述结果支持一个有限判断：在受控测试这一样本上，机制侧的约束使幻觉率为 0，并捕获了一次工具调用误判。

但该判断不宜外推。3.1 节所述”结论可回溯”是对流程的要求，而非对模型能力的验证——前者可以靠机制保证，后者只能靠度量确认。且 5.6.4 节的对照表明，错误特征在不同负载下的分布并不一致，单一样本不足以刻画模型的可靠性边界。可复现性指标在本阶段仍未完成（需在同一目标上重复执行），该度量与框架边界硬化同属下一阶段工作（6.2 节）。

6.0 讨论

6.1 有效性

实验表明，该框架达成了 3.1 节所述的四项设计目标：每阶段报告均标注方法依据；24 个证据文件覆盖全部结论；范围外目标未被触碰，未执行项被显式声明；阶段推进需人工放行。

其中”结论可回溯”的价值在信息收集阶段得到体现：经由 .DS_Store 元数据获得被扫描器遗漏的文件名，并进一步推断出目录快照的时间属性，说明 Agent 对原始输出的阅读能力能够补足规则化工具的盲区。

但需要界定本节结论的适用范围：上述四项验证的都是流程机制是否生效，而非模型能力是否可靠。机制能够保证”结论必须回指证据”，却不能保证”模型不产生被机制捕获之前的错误判断”。5.6.3 节的实测结果显示，在受控测试这一样本上，机制侧约束使幻觉率为 0，并捕获到一次工具调用误判；但该结果建立在单一样本上且可复现性未完成，因此它界定的是已观察到的上界，而非模型的可靠性上限。

6.2 后续工作

按优先级排列：

  1. 模型可靠性的可复现性验证——5.6.3 节已完成幻觉率与工具调用质量的实测，但样本单一。下一步需在同一目标上重复执行，度量两次结论集合的交集比。这是当前剩余的最大缺口：缺少该项，5.6 节的结论只能界定为单样本观察；
  2. 提示注入防护——将目标返回内容视为数据而非指令，实施输入隔离。渗透测试中 Agent 必然读取由目标产生的响应与文件内容，这类输入天然不可信；
  3. 边界硬化——在执行前增加校验环节，使越界请求在实现层面无法发出。当前边界层依赖 Agent 主动读取 scope.json，属”约定型”约束；
  4. 流程引擎——将阶段划分与人机放行实现为受代码约束的状态机。

7.0 结论

本文针对大语言模型应用于渗透测试时的三项结构性障碍——过程不可控、结论不可复现、证据不可审计——提出 Hermes-PentestAgent 框架。

框架的核心不在于其三个组件（Agent、技能库、工具链），而在于组件之上的三层结构：契约层规范工作方式，边界层固化授权范围，证据层要求结论可回溯。

验证表明，该框架能够在保持过程可审计的前提下，完成从信息收集到漏洞验证的完整流程，产出 24 个证据文件与 28 项确认漏洞的完整报告。

本文验证的是流程层面的可控性与可审计性。5.6 节对模型能力的实测显示：在受控测试这一样本上，报告全部结论均可回指证据文件（幻觉率 0%），并有一处工具调用误判被证据交叉比对捕获。但该结果建立在单一样本上，可复现性尚未度量。因此框架的适用前提仍应表述为：约束能够抑制而不能消除模型的臆造风险，其残余风险由 5.6 节所述指标负责持续度量。

1.0 WAF

1.1 简介

WAF (Web应用防火墙, Web Application Firewall) 专门用于保护Web应用免受常见网络攻击的安全工具, 通过监控和过滤HTTP/HTTPS流量, 阻止各种基于Web应用的攻击, 如: SQL注入, XSS, include_file等…

1.2 WAF工作原理

WAF位于用户与Web服务器之间, 作为过滤层检查进入和离开服务器的流量. 当用户请求到达Web应用时, WAF会根据预定义的规则对这些请求进行分析, 并阻止符合攻击特征的请. 例如:

  • 阻止恶意SQL查询, 防止SQL注入攻
  • 拦截恶意的JavaScript代码, 防止XSS
  • 检测文件上传请求中的恶意文件

1.3 WAF的防护原理

WAF之所以能够起到对网络应用的防护作用, 主要是基于以下手段:

  1. 异常检测机制: 拒绝不符合HTTP标准的请求;
  2. 黑名单 / 白名单;
  3. 基于规则和异常的保护: 定义安全规则或异常状态, 对服务器进行安全防护;
  4. 扫描器识别: 对于扫描器特征会进行识别以及拦截

1.4 WAF的类型

  1. 软件型WAF: 本身是一个软件, 部署在服务器上, 检测是否存在Web攻击;

  2. 硬件型WAF: 本身是一款硬件, 可以有多种部署方式, 如果是串联到链路中, 则可以拦截恶意流量, 如果是以旁路的形式部署, 则只能记录攻击但是不能拦截. 硬件型WAF一般而言比软件型WAF更加昂贵, 但是检测速度快, 不易成为网站瓶颈.

  3. 云WAF: 云WAF简单理解为带有WAF功能的CDN, 因为其实现机理与CDN基本相同, 都是通过更改目标站点的DNS记录, 使其指向云WAF, 然后对站点的访问进行过滤. 云WAF通常以反向代理的方式进行工作, 其最大的优点是方便快捷, 但是如果攻击者能够找到站点的真实IP地址, 那么云WAF就存在被直接绕过的风险.

  4. 站点内置WAF: 站点内置WAF, 即网站的开发者考虑到站点的安全性, 将一些过滤功能写成代码, 嵌入到站点内, 或者直接嵌入到页面代码中, 或者以一个单独的文件列出, 然后被相关页面所引用. 这种WAF的灵活性非常高, 因为是直接开发在页面上, 因此可以针对一项非常具体的业务, 乃至一个微小的功能来实现检测和规律, 但是相应的其通用型就比较低了.

1.0 企业安全产品

以下产品分析围绕此维度展开:

  1. 产品作用是什么? 解决了什么问题?
  2. 产品工作原理, 为什么能够实现某个功能/目的?
  3. 怎么操作? 重点功能是什么?

实际建设中，单一安全产品很难覆盖所有风险，通常需要按“边界防护、终端防护、应用防护、运维审计、检测响应、威胁诱捕、远程接入”等方向组合，形成纵深防御体系。

1.1 杀毒软件

  • 检测、预防和清除计算机病毒、恶意软件、木马、蠕虫等恶意程序的安全软件。
  • 作用：解决终端侧已知恶意代码的查杀问题，提供基础实时防护、病毒扫描、文件监控和漏洞修复能力。
  • 原理：通过病毒特征库匹配、启发式检测、行为监控、云查杀、沙箱分析等方式识别恶意文件或进程。特征库负责已知威胁，启发式和行为分析用于补充未知威胁。
  • 重点功能：实时防护、全盘/自定义扫描、隔离区、白名单、病毒库更新、漏洞修复、日志告警。
  • 常见产品：360、火绒、Windows Defender、卡巴斯基等;

1.2 终端安全 EDR

  • EDR（Endpoint Detection and Response，端点检测与响应）是对端点设备如计算机、服务器、移动设备等进行持续监控、检测和响应的安全技术。
  • 作用：识别并应对复杂安全威胁，弥补传统杀毒软件只依赖特征库、难以发现高级威胁和横向移动的不足。
  • 原理：在终端部署 Agent，持续采集进程、文件、注册表、网络连接、命令行、账号等遥测数据；结合 IOC、行为规则、机器学习、威胁情报和云端关联分析，发现异常行为，并支持隔离、阻断、取证等响应动作。
  • 重点功能：实时监控与数据采集、行为分析与威胁检测、自动化响应与修复、事件管理与取证、可视化与报告、威胁狩猎。
  • 常见产品：CrowdStrike、SentinelOne、Microsoft Defender for Endpoint、奇安信天擎、深信服 EDR、火绒企业版等。

1.3 防火墙

  • 防火墙是一种网络安全设备或软件，用于监控和控制网络流量，根据预设安全规则允许或拒绝数据包通过。
  • 作用：实现网络边界访问控制、区域隔离、NAT、VPN、流量日志记录，限制未授权访问。
  • 原理：检查每个通过数据包的头部信息，如源地址、目标地址、端口号、协议类型等，并根据预设规则决定是否允许该数据包通过。现代防火墙还支持状态检测、应用识别、入侵防御、URL 过滤等能力。
  • 类型：个人电脑防火墙、企业防火墙、云防火墙、下一代防火墙 NGFW。
  • 部署位置：个人电脑、企业内部、网络边界、云服务器、VPC 边界等。
  • 重点功能：安全区域、接口与路由、NAT、访问控制策略、会话表、日志监控、默认拒绝、最小化放行。

1.4 WAF

  • WAF（Web Application Firewall，Web 应用防火墙）是专门保护 Web 应用程序和 API 的安全设备或服务。
  • 作用：通过过滤、监控和阻止恶意网络流量及应用层攻击，确保 Web 应用的安全性和数据保护。
  • 原理：通常以反向代理、透明代理或云服务方式解析 HTTP/HTTPS 流量，基于规则匹配、语义分析、机器学习、IP 信誉、频率控制等识别 SQL 注入、XSS、命令执行、文件上传、CC 攻击等。
  • 部署方式：云 WAF、硬件 WAF、软件 WAF、容器 WAF；可串联部署，也可通过流量牵引方式接入。
  • 重点功能：Web 应用安全防护、CC 攻击防护、精准访问控制、虚拟补丁、攻击事件管理、数据安全保护、白名单与误报调优。

1.5 IDS/IPS

  • IDS（Intrusion Detection System，入侵检测系统）用于检测网络或主机中的入侵行为并告警。
  • IPS（Intrusion Prevention System，入侵防御系统）在检测基础上进一步阻断攻击流量。
  • 作用：发现扫描、漏洞利用、恶意流量、暴力破解、木马通信等攻击行为，解决“看不见攻击”和“无法及时阻断”的问题。
  • 原理：通过特征匹配、协议解析、异常行为分析、威胁情报等方式识别攻击。IDS 通常旁路部署，镜像流量检测；IPS 通常串联部署，在线阻断。
  • 重点功能：规则更新、告警分级、阻断策略、白名单、流量抓包、日志联动、与防火墙/态势感知联动。
  • 注意点：IPS 串联部署时误报可能影响业务，需要充分测试和调优。
  • 常见产品：Snort、Suricata、Zeek、深信服 IPS、启明星辰天清等。

1.6 态势感知

  • 态势感知是面向全局安全数据的综合分析与展示平台，通常融合 SIEM、SOC、威胁情报、UEBA、SOAR 等能力。
  • 作用：解决安全数据分散、告警过多、事件关联困难、响应慢的问题，帮助安全团队“看清资产、看清威胁、看清攻击链”。
  • 原理：采集流量、终端、日志、漏洞、资产、账号、威胁情报等多源数据，通过大数据存储、关联分析、规则模型、机器学习和攻击链还原，形成安全态势、告警、工单和报表。
  • 重点功能：资产梳理、日志接入、规则与模型配置、安全看板、告警处置、攻击溯源、工单闭环、报表输出。
  • 常见产品：奇安信态势感知、深信服 SIP、阿里云云安全中心、Splunk、ELK 等。

1.7 堡垒机

  • 堡垒机是集中运维审计与访问控制系统，用于管理服务器、网络设备、数据库等资产的运维入口。
  • 作用：解决运维账号共享、权限混乱、操作无审计、事后难溯源等问题，实现“事前授权、事中监控、事后审计”。
  • 原理：通过代理或网关方式接管 SSH、RDP、数据库等协议，统一认证、账号映射、权限控制、会话录制、命令审计和密码托管。
  • 重点功能：资产纳管、用户与角色、授权策略、双人授权、会话录像、命令阻断、密码托管、操作报表、工单审批。
  • 常见产品：JumpServer、齐治、行云管家、深信服堡垒机等。

1.8 蜜罐

  • 蜜罐是一种主动防御技术，通过部署仿真服务、系统或漏洞，诱捕攻击者并记录其行为。
  • 作用：发现扫描、探测、入侵和横向移动，收集攻击情报，拖延攻击时间，弥补传统检测手段对未知威胁的不足。
  • 原理：蜜罐伪装成真实业务或脆弱系统，吸引攻击者访问。攻击者一旦交互，系统即记录 IP、工具、payload、攻击路径等信息，并产生高置信度告警。
  • 类型：低交互蜜罐、高交互蜜罐、蜜网、欺骗防御系统。
  • 重点功能：仿真服务、端口监听、告警联动、攻击取证、IOC 提取、封禁联动。
  • 注意点：部署时需做好隔离，避免蜜罐被攻陷后成为跳板；同时注意隐私与合规。
  • 常见产品：T-Pot、HFish、奇安信蜜罐、默安幻阵等。

1.9 VPN

  • VPN（Virtual Private Network，虚拟专用网络）用于在公网上建立加密隧道，实现远程安全接入或分支互联。
  • 作用：解决远程办公、运维接入、分支通信中的传输安全和身份认证问题，让用户安全访问内网资源。
  • 原理：通过 IPsec、SSL/TLS、WireGuard、OpenVPN 等协议，对数据进行加密、封装和认证，在客户端与 VPN 网关之间建立安全隧道。
  • 类型：IPsec VPN、SSL VPN、远程接入 VPN、站点到站点 VPN。
  • 重点功能：用户认证、证书管理、MFA、权限控制、隧道配置、客户端管理、访问日志、审计。
  • 安全建议：不要只认证不授权，应遵循最小权限原则；及时修补 VPN 设备漏洞；开启 MFA；记录并审计登录与访问行为。
  • 常见产品：OpenVPN、WireGuard、Cisco AnyConnect、深信服 SSL VPN、华为 VPN 等。

1.10 常见组合思路

  • 边界防护：防火墙 + IPS + WAF + VPN
  • 终端防护：杀毒软件 + EDR
  • 应用防护：WAF + 代码审计 + RASP
  • 运维审计：堡垒机 + 日志审计 + 数据库审计
  • 检测响应：IDS + 态势感知 + 蜜罐 + SOAR
  • 体系建设原则：最小权限、默认拒绝、纵深防御、零信任、持续验证、闭环响应。

安全产品不是越多越好，而是要根据业务场景、资产重要程度、攻击面和运维成本进行选型与联动。单点产品解决单点问题，体系化协同才能提升整体安全效果。

1.3 SpringBoot Actuator未授权漏洞

01 基础:

Spring是java web开发常见的框架, SpringBoot是 Pivotal 团队(Spring 官方团队), 开发的快速开发框架, 基于 Spring Framework, 简而言之, SpringBoot就是一个轻量级, 简化配置和开发流程的web整合框架.

Actuator是SpringBoot框架中的功能模块, 它提供了一系列用于监控和管理SpringBoot应用程序的端点(endpoints). 这些端点可以通过HTTP, JMX(Java Management Extensions)或其他一些远程方式访问, 用于查看应用程序的各种运行时信息和健康状态.

SpringBoot Actuator未授权访问漏洞: 攻击者未进行身份验证的情况下访问敏感的管理端点, 从而获取关键应用程序信息或执行某些管理操作. 这种漏洞的存在可能导致严重的安全问题, 如: 信息泄露, 应用程序篡改或拒绝服务攻击.

02 端点信息:

SpringBoot 1.x版本默认内置路由根路径以/开始, 2.x 统一以 /actuator 开始, springboot 1.x 的Actuator Web所有端点默认开启,可直接使用. Springboot 2.xActuator Web端点只有/health和/info默认开启, 访问其它端点, 需要在配置文件application.properties中配置开启.

SpringBoot Actuator主要功能包括:

  1. 健康检查(Health Check): 提供一个用于检查应用程序健康状况的端点. 通过访问/actuator/health端点, 可以查看应用程序是否正常运行. 它对于实时监控应用程序的健康状态和故障排查非常有用.

  2. 应用程序信息(Application Information): 提供了关于应用程序的一些基本信息, 如应用程序名称, 版本号, 描述等, 通过访问/actuator/info端点, 可以获取这些信息.

  3. 环境配置信息(Environment Information): 提供了应用程序的配置属性信息. 通过访问/actuator/env端点, 可以查看应用程序配置属性及其值.

  4. 线程转储(Thread Dump): 提供了获取应用程序线程转储的端点, 通过访问/actuator/threaddump端点, 可以查看应用程序线程当前状态, 用于分析线程问题和死锁情况.

  5. 度量指标(Metrics): 提供了关于应用程序性能和资源利用的度量信息. 通过访问/actuator/metrics端点, 可以查看请求统计, 内存使用, 垃圾回收等指标.

  6. 管理端点(Management Endpoints): 除了上述常用端点外, Actuator还提供了其他管理端点, 如刷新配置, 关闭应用程序等…

    重点关注: info & health端点一般不会被认定为漏洞, 不包含有害信息; env端点若能获取到信息必定有漏洞, metrics端点可能存在接口泄露或包含Cookie & Token & JWT信息.

  • 影响范围统计:

    SpringBoot版本 默认开放端点 风险等级
    < 1.x 所有端点 高危
    2.0.x - 2.3.x 仅 /health 和 /info 中危 (info)
    ≥ 2.4.0 仅 /health 低危

    SpringBoot Actuator 端点默认开放, 攻击者通过访问这些敏感管理端点, 获取关键应用程序信息或执行某些管理操作.

env信息脱敏利用逻辑分析:

  • SpringBoot脱敏只发生在”输出阶段” (写HTTP响应时)

    访问/actuator/env/时, SpringBoot会调用Sanitizer(净化器)类来序列化数据, 遍历所有 PropertySource, 检查属性名的关键字如: password, secret, command, key 等. 若匹配关键字, 它会用 ****** 替换该属性的 value 字符串, 然后再将这个被替换后的 JSON 输出给浏览器. (只读副本替换, 未修改JVM 堆内存中原有的 String 对象)

  • HeapDump 抓取的是“存储阶段”(内存中的原始对象)

    /actuator/heapdump 端点利用 JVM 的 hprof 二进制格式, 将整个 JVM 堆内存(Heap)原封不动地序列化并导出为文件. 直接读取 JVM 运行时数据区的所有字节, 导出的 heapdump 文件中, 包含未被脱敏的原始字符串

  • 工具: 绕过输出阶段, 直接读取存储阶段的数据.

    JDumpSpider 在本地运行, 完全脱离 SpringBoot 控制

    工具逻辑链:

    • 解析结构: 解析 .hprof 文件的二进制格式, 重建出 JVM 中的对象图(Object Graph)
    • 定位目标: 它内置针对SpringBoot的 “爬虫规则” Spider, 专门去查找 OriginTrackedMapPropertySource, MutablePropertySources 或 System.getProperties() 对应的 Hashtable 实例.
    • 深度遍历: 遍历这些 Map 或 Properties 对象的 Entry(键值对). 当找到键为 sun.java.command 的 Entry 时, 它会顺着该 Entry 的 value 引用, 直接读取内存中那个 String 对象的 char[] 数组.
    • 还原明文: 将 char[] 重新编码为 Java 字符串并打印.

为什么脱敏无法保护内存 ?

  • 传输/展示安全: ****** 只保护了”网络传输” 和 “页面展示”这一瞬间.
  • 运行时安全: 只要程序要使用这个路径去启动 JAR 包, 那么 JVM 的类加载器(ClassLoader) 就必须持有这个字符串的明文引用.

1.0 中间件安全

1.1 什么是中间件?

中间件(Middleware) 是指一种软件组件, 作用是在不同系统, 应用程序或服务之间传递数据和消息, 通常位于应用程序和操作系统之间, 负责在不同的应用程序之间传递数据, 协调不同应用程序之间的通信, 以及处理网络请求等.

中间件通常是插件式架构, 允许被集成到现有应用程序中, 可提供如: 身份验证, 授权, 缓存, 负载均衡, 日志记录, 安全性等功能, 以求简化应用程序的开发和部署过程.

  • 广义: 涵盖了从web服务器到身份验证系统, 再到消息传递等一切内容
  • 具体: Jboss Weblogic Tomcat Apache等

1.2 中间件漏洞

中间件漏洞是指在中间件软件中存在的安全漏洞, 通常包含以下几种:

  1. 代码注入漏洞: 向中间件发送恶意代码, 执行任意代码或获取敏感数据;
  2. 跨站脚本漏洞: 在中间件输出的网页中插入恶意脚本, 来窃取用户信息或进行其他恶意行为;
  3. SQL注入漏洞: 对中间件输入的SQL查询中插入恶意代码, 执行任意SQL查询或获取敏感数据;
  4. 认证和授权漏洞: 攻击者可以利用中间件的认证和授权机制的漏洞, 来绕过访问控制, 获取系统权限;
  5. 文件包含漏洞: 攻击者可以利用中间件的文件包含功能, 来包含恶意文件并执行任意代码.

1.1 基础

序列化是将内存中的对象转换为字节序列或字符串的过程, 以便于存储, 传输或在网络传递.

反序列化则是将字节序列或字符串还原为原始对象.

漏洞原理: 反序列化漏洞的本质: 攻击者可控的恶意数据被程序信任并还原为对象, 而程序未对输入进行严格验证.

1.0 JWT基础

1.1 什么是JWT?

定义:

JWT (JSON Web Token) 是一个开放标准, 定义了一种紧凑且自包含的方式, 用于在各方之间以 JSON 对象的形式安全传输信息. 令牌本身包含了所有必要的用户信息, 服务端无需额外存储会话状态

特点:

  • 紧凑: 体积小, 适合通过URL, POST 参数, HTTP Header 传递
  • 自包含: 携带用户ID, 角色等关键信息, 减少数据库查询
  • 跨域: 天然支持跨域认证, 适合微服务和前后端分离架构

核心应用场景

场景 说明
认证 用户登录后, 后续请求携带 JWT 即可访问受保护资源
信息交换 使用公钥/私钥对签名, 确保发送方身份可信

1.2 JWT 与 Session的区别(为什么需要 JWT?)

传统 Session 认证问题:

  • 服务端需要存储 Session, 分布式环境下需共享存储(如Redis), 增加复杂度
  • 存在单点故障风险
  • 扩展性受限, 新增服务实例需同步认证状态

1.3 JWT 核心结构

一个完整的 JWT 由三部分组成, 用点号分隔 '.'

01 Header (头部)

描述 JWT 的元数据, 是一个 Base64Url 编码的 JSON对象

alg 字段指定签名算法, typ 固定为JWT

02 Payload (荷载)

JWT 的主体内容, 包含需要传递的声明

注册声明(Registered Claims) – 预定义的标准字段

声明 全称 含义
iss Issuer 签发者
exp Expiration Time 过期时间(必须使用Unix时间戳)
sub Subject 主题(通常为用户ID)
aud Audience 受众
nbf Not Before 在此时间之前不可用
iat Issued At 签发时间
jti JWT ID JWT 唯一标识

公共声明(Public Claims) : 自定义字段, 用于传递非敏感信息, 如用户ID, 角色.

私有声明(Private Claims): 双方约定的自定义信息.

重点: Payload 仅 Base64 编码, 不是加密, 任何能拿到Token的人都可解码读取内容.

03 SIgnature (签名)

对 Header 和 Payload 进行签名, 用于验证令牌的完整性和真实性.

HS256 对称签名

两种主流签名算法对比:

算法 类型 特点 场景
HS256 对称加密 同一密钥签名和验证, 密钥不能泄露 单一服务端内部使用
RS256 非对称加密 私钥签名, 公钥认证 分布式系统, 第三方验证

1.4 JWT 工作原理

以下 JWT 验证流程图解

流程:

  1. 用户登录: 客户端向服务端发送用户名和密码
  2. 服务器验证: 验证凭据是否正确
  3. 生成 JWT: 使用密钥签名, 编码用户信息(如 ID, Role) 和过期时间
  4. 返回客户端: 将 JWT 返回给客户端
  5. 客户端存储: 通常存储在localStorage或 Cookie中
  6. 携带 JWT 请求: 后续请求在Authorization: Bearer <JWT>Header中携带
  7. 服务器验证: 验证签名和有效期, 通过则允许访问

2.0 JWT 常见漏洞与攻击手法

  • alg: none 攻击

    将 Header 中的alg改为none, 并删除签名. 部分有缺陷的库会直接接受未签名的Token

    • 影响: 完全绕过身份验证, 可伪造任意用户身份

    • 利用: jwt_tool -X a

  • 算法混淆攻击(RS256 → HS256)

    利用非对称加密 (RS256) 和对称加密 (HS256) 的差异, 攻击者获取公钥后, 将其作为 HMAC 的 “密钥” 伪造Token

    原理: 服务端期望 RS256 验证, 但攻击者将算法改为 HS256, 用公钥作为对称密钥签名.

  • 弱密钥爆破

    如果 JWT 使用 HS256 且密钥太弱 , 可用社工字典暴力破解.

  • kid 参数注入

    kid (Key ID) 用于指示服务器使用哪把密钥验证, 若输入过滤不严, 可进行:

    • 路径遍历: ../../dev/null (使服务器使用空密钥)
    • SQL注入: 操纵密钥查询逻辑

  • jku (JWK Set URL) 注入

    jku 告诉服务器去哪里获取公钥, 若服务器未校验该URL, 攻击者可将其指向自己控制的服务器, 用自己生成的密钥伪造Token

  • 信息泄露

    Payload 仅 Base64 编码, 不是加密, 攻击者可轻易解码读取其中的敏感信息
